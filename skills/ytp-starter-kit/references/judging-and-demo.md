# 評分、Demo 與當天規則

> 整理自主辦方 11/14 相見歡的說明，一切以主辦方正式公告為準。

## 評分

| 項目 | 比重 | 評審看什麼 |
|---|---|---|
| 完成度 | 50% | 評審能獨立操作核心流程嗎？換一筆資料還能跑嗎？AI 出錯時怎麼處理？ |
| 創新性 | 30% | 不可取代性（競品比較）：和直接問 ChatGPT 這類聊天機器人或現有工具相比，在哪個具體步驟改善了使用者的困難？ |
| 教育價值與契合度 | 20% | 適切度：功能和使用時機是否對準要幫的人？使用者要自己做什麼思考？之後有什麼小任務能看出他理解了？ |

功能多寡、畫面數量、模型數量不直接加分。評審實際操作產品評分；AI 會依事先公布的準則讀 repo 作為佐證，文件多不等於加分。

幫隊伍做取捨時，優先順序是：核心流程穩定可操作 → 換資料、出錯都不會壞 → 在某個步驟明顯比聊天機器人好 → 其他。

## 初選桌邊 Demo（5 分鐘）

| 時間 | 內容 | 開發時要準備的東西 |
|---|---|---|
| 30 秒 | 誰卡在哪裡、作品想改變什麼 | 一句話的使用情境 |
| 2 分鐘 | 評審自己操作核心流程 | 一條不需要解釋就能走完的流程 |
| 1 分鐘 | 一次引導前後使用者的表現 | 一組前後對照（例如同一題引導前後的回答） |
| 1 分 30 秒 | 抽換案例、看失敗處理、提問 | 能從資料包換一筆輸入；出錯時有清楚的畫面 |

決選另有 Demo＋簡報 8 分鐘。

## Repo 規則

- 作品主體必須當天完成；賽前的試作放在 `pre-race` 分支。
- README 寫明使用的 LLM 模型與版本。
- API key 不要寫進 repo。
- 哪些賽前成果可以沿用（例如介面骨架、資料讀取、對拍工具），主辦方確認後會再公告。

## 賽前四項自我檢查

1. 完整跑過一次流程：範例資料 → 使用者輸入 → AI 回應 → 檢查 → 介面顯示。
2. 處理過一次出錯：格式錯誤、答案不合理或逾時，工具還能繼續用；至少真的呼叫過一次模型。
3. 找一位真的使用者試用，記下他在哪一步需要解釋。
4. 寫出一個學習假設：幫誰、在什麼時候、透過什麼互動、學會什麼，又要怎麼觀察到。
